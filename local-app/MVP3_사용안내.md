# MVP3 1차 구현 (2026-11-16)

실행: 프로젝트 폴더에서 `npm run app:start` → http://127.0.0.1:4313/#schedule
종료: `npm run app:stop`. 기존 Mac 실행·종료 파일도 동일하게 사용합니다.

## 사용 순서
1. 고객·현장 관리에서 현장을 등록합니다.
2. 공정·발주·견적의 자재 단가, 단위, 공급처, 평일 납기를 입력합니다. 기본 자재 3개는 가상 연습 자료입니다.
3. 현장 선택 → 견적 → 자재 행 추가, 수량(소수 3자리), 여유율, 인건비·기타비·할인·직접 지정 세율 입력 → 미리보기 → 저장.
4. 저장 문서에서 승인 또는 반려합니다. 반려 이유는 필수입니다. 수정·재검토로 수정하면 버전이 증가하고 승인이 해제됩니다. 자재 단가는 수정 저장 시 현재 값으로 다시 계산합니다.
5. 공정표: 착공일, 제외 휴무일, 순서별 공정명·일수·평일/달력을 입력합니다. 순차 계산이며 양생은 달력 일수로 설정합니다.
6. 발주 요청: 자재, 수량, 현장 필요일, 여유 평일 입력. 자재 납기+여유만큼 주말을 제외해 권장 발주일을 계산합니다. 승인 → 실제 공급처에 직접 주문 → 발주 완료 기록 → 실제 수령 → 입고 완료 기록 순서입니다.

금액은 원 단위 반올림(항목 금액 및 세액 각각), 합계는 항목+인건비+기타비-할인+세액입니다. 세율 기본값은 0이며 사용자가 지정합니다. 공정의 휴무일은 직접 입력해야 하고 발주 역산은 주말만 제외합니다.

## 저장 구조
- `backend/migrations/008_operations.sql`
- `materials_catalog`: 자재 현재 단가·공급처·납기, 수정 충돌 방지 revision
- `operation_documents`: projects 1:N 문서(estimate/schedule/order), 종류별 계산 결과·자재 스냅샷 JSON, 상태·버전
- `operation_reviews`: 문서 1:N 승인/반려/발주/입고 기록, 당시 문서 스냅샷. 같은 버전·결정 중복 금지
- 프로젝트/문서 삭제 RESTRICT. 원본 승인 기록을 보존합니다. 기본 타임스탬프 및 변경 시 updated_at 적용.
- 기존 로컬 SQLite 경로·전체 백업 ZIP·복원 체계를 그대로 사용합니다. 새 테이블도 전체 DB 백업에 포함됩니다. 복원한 구버전 DB는 실행 시 008까지 마이그레이션됩니다.
- API: GET /api/operations, POST /api/materials, POST /api/operations/preview, POST /api/operations, POST /api/operations/:id/review
- 데이터 확인: http://127.0.0.1:4313/database

## 검증 및 범위
기존 16개+MVP3 2개 테스트 통과. 소수 수량·반올림, 저장 시 단가 보존, 수정 후 재승인, 충돌 방지, 승인 전 발주 기록 차단, 입고 순서, 휴무·주말·양생, 잘못된 날짜/음수 거절, 마이그레이션 재실행을 검증했습니다.

이번 버전은 수동 입력·계산·내부 승인·저장입니다. 공정 간 병행/의존관계, 공급처 API 실제 주문, 서버 직접 PDF 생성, 단가 변경 이력 화면, 재고·부분입고, 업무보드 통합은 후속 작업입니다. AI가 견적 금액이나 공정 일수를 자동 판단하지 않습니다. 공개 데모와 분리된 로컬 기능입니다.


## 2차 연결 (2026-11-16)
- 승인 견적 카드의 **자재별 발주 요청 만들기** → 필요일·여유 평일 입력 → 자재 행마다 검토용 요청 생성. 인건비·기타비·세금은 자재 발주에 포함하지 않습니다.
- 원본 견적 ID·버전·행 번호를 관계로 보관하고 중복 생성을 막습니다. 반복 요청은 기존 요청을 반환하므로 날짜 변경은 적용되지 않습니다.
- 수량은 여유율 포함 후 0.001단위 올림이며 금액은 그 발주 수량으로 계산합니다. 견적의 단가·명칭·단위·공급처를 보존하고 납기는 생성 당시 단가 DB에서 가져옵니다. 이후 설정 변경은 기존 요청을 바꾸지 않습니다.
- 연결된 요청은 원본 추적을 위해 직접 수정하지 않습니다. 반려·일정 변경이 필요하면 원본 견적을 수정·재승인하고 새 버전에서 생성하세요. 이전 발주/입고 기록은 남습니다.
- 원본이 수정되거나 미승인 상태가 되면 기존 요청의 승인·발주를 서버에서 차단합니다. 이미 발주한 건의 실제 입고 기록은 계속 남길 수 있습니다.
- **업무 보드 → 견적·공정·발주 검토함**에서 조회·승인·반려 및 직접 처리한 발주·입고 기록이 가능합니다. AI 원고 목록과 문서 검토함의 필터는 각각 적용됩니다. 메뉴의 검토 건수는 두 목록을 합산합니다.
- 승인 견적의 **견적서·PDF 저장** → 인쇄용 화면 → **인쇄·PDF로 저장**. Mac 인쇄 창의 PDF 메뉴 또는 Windows PDF 프린터를 사용합니다. 서버가 PDF 파일을 직접 생성·다운로드하는 방식은 아닙니다. 출력 화면에는 내부 공급처 정보와 승인 댓글을 노출하지 않습니다.
- 추가 API: POST `/api/operations/:id/orders`, GET `/api/operations/:id/print`.
- 마이그레이션 `009_estimate_orders.sql`: 원본 문서 FK(RESTRICT), 버전·행 번호 및 UNIQUE 인덱스. 전체 SQLite 백업에 함께 포함됩니다.
- 이번 검증: 기존 기능 포함 테스트 20개. 실제 화면에서 견적 v2 → 발주 요청 생성 → 업무 보드 승인 → 새로고침 후 상태 유지 및 출력 레이아웃을 확인했습니다. 공급처 자동 주문, 재고·부분입고는 미구현입니다.


## 3차 연결: 공정과 자재 필요일 (2026-11-16)
1. 같은 현장의 공정표를 작성하고 승인합니다.
2. 발주 요청 카드(업무 보드 또는 공정·발주·견적)의 **공정 연결·일정 갱신**을 누릅니다.
3. 승인 공정표와 자재를 사용할 공정을 선택합니다. 공정 시작일이 자재 필요일이 되고, 저장된 납기+여유일만큼 평일을 거슬러 권장 발주일을 자동 미리보기합니다. 주말과 공정표의 지정 휴무일은 제외합니다.
4. 변경 메모를 남기고 저장합니다. 요청 버전이 증가하며 검토 필요로 변경됩니다. 수량·단가·공급처·납기는 그대로 보존합니다. 금액 변경은 견적에서 진행합니다.
5. 다시 승인 후 실제 공급처에 직접 주문하세요. 공정표가 수정되면 연결된 요청에 일정 변경 경고가 표시되고, 승인·발주 기록은 차단됩니다. 최신 공정표를 승인하고 다시 연결·검토해야 합니다.

이미 발주·입고한 건의 필요일은 덮어쓰지 않습니다. 실제 일정 조정은 공급처와 확인하세요. 이미 발주한 건은 공정표 수정 후에도 입고 완료 기록을 남길 수 있습니다. 같은 연결을 다시 저장하면 불필요한 중복 버전을 만들지 않습니다. 반려된 건을 다시 연결해 제출하면 재검토 버전으로 남깁니다.

저장: `010_order_schedule.sql`의 공정표 FK·버전·공정 순번, `order_schedule_changes` 변경 전후 스냅샷·메모. 삭제는 RESTRICT, (발주 ID, 버전) UNIQUE. 전체 백업에 포함되며 DB 확인 화면에서 조회할 수 있습니다.

API: POST `/api/operations/:id/schedule-preview` (조회용 계산), POST `/api/operations/:id/schedule` (연결 저장). 요청의 발주 버전과 공정표 버전을 검사합니다. 다른 현장의 공정표나 미승인 공정표는 연결할 수 없습니다.

테스트 22개: 기존 기능, 휴무일 역산, 재승인, 버전 충돌, 다른 현장 연결 차단, 변경 공정표에서 발주 차단, 발주 후 수정 차단, 입고 유지, 변경 이력 및 반려 후 재제출·파일 재실행 보존을 확인했습니다. 화면에서는 가상 현장의 마감 공정 → 필요일 2026-11-30, 권장 발주일 2026-11-19를 저장·재조회했습니다.


## 4차 연결: 발주·입고 현황판 (2026-11-16)
사무실 대시보드의 **발주·입고 확인할 일**에서 현장과 상태를 골라 보고 **업무 확인**을 누르면 해당 발주 요청으로 이동합니다. 입고 완료 건은 제외하며 외부 주문·납품 추적·메시지 전송은 실행하지 않습니다.

분류는 서버의 Asia/Seoul 날짜 기준입니다.
- 재검토 필요: 미발주 건의 원본 견적/공정표 변경 또는 반려. 날짜 경고보다 먼저 표시합니다.
- 발주일 경과: 권장 발주일이 지났으나 발주 완료 기록이 없음.
- 발주 임박: 권장 발주일이 오늘부터 3일 뒤까지(달력 일수, 양끝 포함).
- 발주 예정: 임박 범위 이후 권장 발주일.
- 입고 지연: 발주 기록이 있고 필요일이 지났으나 입고 완료 기록이 없음. 실제 배송 지연을 조회한 결과가 아닙니다.
- 오늘 입고 예정: 발주 기록이 있고 필요일이 오늘.
- 입고 대기: 발주 기록이 있고 필요일이 미래.

이미 발주된 건은 입고 기준으로 분류하며 원본 변경 여부는 추가 경고로 표시합니다. 분류끼리 중복 집계하지 않습니다. 현장 선택 시 요약 건수도 해당 현장으로 제한합니다. 같은 현황판 안의 상태 선택을 적용합니다. 조회 시각과 실패 시 이전 결과임을 표시합니다.

앱 화면이 열린 동안 60초 간격, 오래 숨겼다가 다시 표시할 때, 문서 처리 후, 다시 조회 버튼으로 최신화합니다. 화면의 값은 별도 테이블로 복제하지 않고 기존 DB에서 계산합니다. `GET /api/order-dashboard`, `backend/order-dashboard.ts`, `frontend-demo/order-dashboard.js`. 공개 데모에 고객 DB를 올리지 않습니다.

테스트 24개 통과: 한국 자정, 연말·윤년 경계, 3일 범위, 발주/입고 상태 분리, 완료 건 제외, 재검토 우선순위 및 조회 시 원본 데이터 불변. 실제 화면에서 필터·다시 조회·업무 바로가기를 확인했습니다. 가상 데이터 2건은 발주 임박, 입고 지연 0건입니다.
